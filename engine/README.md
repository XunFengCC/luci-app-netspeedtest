# netspeed engine

Proxy integration uses an explicit `--http-proxy 127.0.0.1:PORT` and a display-only `--proxy-name`. HTTP CONNECT leaves HTTPS target DNS to that proxy, and a failed proxy never retries directly. `transport_peer_ip` identifies the loopback peer in proxy results; only direct results use `peer_ip` for the actual server connection. `--source` and proxy mode cannot be combined. Direct auto-selection compares domestic providers, proxy auto-selection compares the catalog concurrently; healthy warm HTTP RTT is the selection criterion, not maximum bandwidth.

`--custom-file PATH` loads at most 20 validated LibreSpeed services. `validate-custom` reads and validates that file without starting network activity, enabling atomic controller persistence. HTTP/HTTPS bases exclude credentials and fragments; endpoints must be relative paths. Country metadata is supplied by the catalog/custom user, never inferred from a target IP. The public catalog is explicit and can retain temporarily unreachable nodes for manual proxy use; metadata discovery never downloads the payload or invokes telemetry/getIP.

This CLI adapts the LibreSpeed Go measurement core (`github.com/librespeed/speedtest-cli` v1.0.14, tag commit `42e5f76c90e64e04ab7079fd76d833dfe41805da`) to the router worker's JSON/NDJSON contract. The binary is statically linked; distribute the corresponding engine source, these notices, and the terms that let recipients relink the application with a modified LibreSpeed library. Dependency license texts are retained under `vendor/`. See [NOTICE](NOTICE) for the pinned source, local fork, and build details.

Build from this directory with Go 1.26 or newer (validated with Go 1.27.1):

```sh
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -mod=vendor -trimpath \
  -ldflags='-s -w' -o /path/to/ignored/netspeed-engine .
```

Global flags precede the command. `--source` accepts an IP address or a Linux interface name. `--connections` controls parallel download streams (default 8) and `--upload-connections` controls parallel upload streams (default 4); each accepts 1–8. `--duration N` sets the measurement window in whole seconds, bounded to 3–10 and defaulting to 8. Download and upload controls remain separate so tuning one does not change a single flag's meaning. `--uid N` clears supplementary groups and changes GID/UID before creating clients or performing network activity. `--dns` sets the direct DNS resolver (default `223.5.5.5:53`). Proxy environment variables are removed and the HTTP transport has no proxy, because results must describe direct egress.

`servers` prints a JSON array after lightweight checks. It performs USTC's documented public proof-of-work handshake where required and three empty ping requests per candidate (the first is discarded); it does not call `getIP`, telemetry, or throughput endpoints. The catalog contains USTC id `10001`, Southeast University id `10002`, Singapore id `68`, and Tokyo id `82`. Southeast University's official page at `https://xnfz.seu.edu.cn/speed/` declares `empty.php` ping/upload and `garbage.php` download endpoints. Endpoint checks confirmed empty GET and POST responses and a small garbage response; requests need a provider-scoped `Mozilla/5.0` User-Agent. That override is applied only to SEU requests. One full SEU run succeeded, but a later repeated short test returned HTTP 403 with an HTML upload response. A healthy empty ping therefore does not guarantee upload availability; the engine keeps that failure as an error and records no result. `run auto` probes healthy mainland candidates and selects the lowest warm-connection latency; if none are reachable it errors instead of falling back to a foreign node. Each server object includes the connected endpoint's `peer_ip`, recorded from the remote address of a successfully established TCP socket after the system's address-family fallback, and `country_code` for the UI. The USTC challenge/cookie is kept only in the in-memory per-run cookie jar and is never printed or written to disk.

The measurement core uses LibreSpeed's empty HTTP endpoint for ten sequential idle probes and discards the first probe to avoid connection setup skew. Latency is the arithmetic mean of the remaining nine request/response round trips. Jitter follows LibreSpeed's smoothed absolute-difference estimate: for each adjacent retained pair, `d = abs(current - previous)`; if the current jitter estimate is greater than `d`, update to `0.7*jitter + 0.3*d`, otherwise update to `0.8*jitter + 0.2*d`. The first difference seeds the previous measurement; smoothing starts with the following difference and an estimate of zero. Discovery uses one such request as an availability/latency check.

Download and upload run 8 and 4 parallel workers by default for an eight-second measurement window, with a 200 ms stagger between worker starts. The CLI controls the counts and duration separately; the result reports `download_connection_count` and `upload_connection_count`. `connection_count` remains as a compatibility alias for the download count. A shared 3 GiB per-run payload budget bounds the two phases; each direction is capped at eight workers. At 500 ms intervals the callback reports the cumulative average rate since the phase counter started (`payload bytes / elapsed seconds`), in decimal Mbps (`bytes/s * 8 / 1,000,000`). These are time-series samples of cumulative averages, not 500 ms window rates or EWMA values. The final rates use the same byte-counter average. Download counts response body bytes actually read from successful non-HTML 2xx responses. Upload counts payload bytes only after the server returns 2xx, the full request body was consumed, and its response body was read successfully; this is application-level confirmation, not a TCP acknowledgement count. A result requires the measurement window to complete, at least one valid payload transfer, and workers to remain able to continue; if every worker fails before the window ends, the phase errors instead of returning an early partial rate. Reaching the byte budget early also errors rather than recording a partial-window result. The result event reports confirmed `download_bytes` / `upload_bytes`, target `phase_duration_seconds`, and each observed phase duration (which includes worker startup stagger). An external cancellation/deadline, no successful transfer, invalid HTTP response, or nonpositive/nonfinite final rate produces an error.

`GOMEMLIMIT=48 MiB` semantics are applied through Go's runtime soft memory limit and `GOGC=50`. This is a runtime target, not a peak-RSS guarantee. Discovery has a 20-second overall deadline and each workflow a 75-second deadline; ping has a 10-second deadline, and each transfer phase gets its configured duration plus five seconds for teardown. Fake-server and endpoint checks do not establish throughput; the router A/B results and the receive-buffer experiment are recorded below.

## Local verification

The local fake-server tests cover USTC proof challenge solving and cookie retention, provider selection, rejection of HTML/non-2xx responses, actual download byte callbacks, confirmed-upload accounting, failure after partial bytes, zero-valued jitter JSON, transfer budget handling, and external cancellation. On the development host, `go test -mod=vendor ./...`, `go test -race -mod=vendor ./...`, and `go vet -mod=vendor ./...` passed. The Linux-only socket test dials a local TCP listener and reads back `SO_RCVBUF`; it was cross-compiled for ARM64 but must be run on Linux or the router to validate that platform path. The pinned USTC endpoint was checked through the actual `servers`/`checkProvider` path after proof of work: its empty ping returned 2xx, discovery reported its connected target address as `202.141.176.43`, and no throughput endpoint was called.

## Router receive-buffer experiment

Review of the client path found no throughput throttle: download workers use `io.Copy` to consume each response body; the 500 ms ticker only reports the cumulative byte counter and does not pause reads. The 3 GiB value is a per-run safety ceiling, not a rate limit. On 2026-10-04, four download/four upload streams over an eight-second window measured 130.37/26.08 Mbps on the router. Eight download/four upload streams over the same window measured 195.47/26.08 Mbps (229,891,576 download bytes over 9.4082 seconds; 28,049,408 confirmed upload bytes over 8.6036 seconds), versus 207.55/29.68 Mbps on the same engine and target on the development Mac. The selected default of 8/4/8 brings the router download result close to that comparison while reported RSS was about 11 MiB and CPU was not saturated. Earlier three-second tests were variable: 4 streams measured 80.65 Mbps down on the router, 8 streams measured 166.12; after applying the receive-buffer request, 4 streams measured 125.72 and 8 streams 159.29. These short-window results do not prove that receive buffers caused the differences or that the issue is solved.

For a bounded experiment, Linux measurement TCP sockets request `SO_RCVBUF=212992`, matching the router's reported `net.core.rmem_max`; this is applied by the process's `net.Dialer.Control` callback, not by changing a global sysctl. The result records per-direction connection counts. An explicit `SO_RCVBUF` locks receive-buffer autotuning for that socket, so it may hurt a higher-RTT route or a system with different buffer settings; compare the short-window router result before keeping this setting. Revisit or remove it when the router kernel limit or WAN latency changes. The local host tests do not exercise this Linux socket option, and throughput acceptance remains a router-side integration test. The router's eight-download/four-upload/eight-second SEU run used the server's IPv6 peer and completed with 191.31/3.66 Mbps; the upload bytes were confirmed, but that single node result does not identify the cause of its low upload rate. The actual network stack address-family choice is retained rather than forcing IPv4.

The wrapper-side fork is intentionally narrow and lives in `vendor/github.com/librespeed/speedtest-cli/defs/`: `server.go` adds a per-run HTTP client/referer and cancellable HTTP ping; `adapter.go` exposes cancellable, callback-driven transfers with response validation and shared byte-budget support; `bytes_counter.go` adds an atomic payload commit method. These additions retain LibreSpeed's repeated parallel request approach and counter-based average-rate calculation, while making the web protocol behavior safe for this worker. Re-run the tests after changing upstream versions or regenerating `vendor/`; `go mod vendor` replaces the local fork.

The vendored build has 11 external Go modules (18 imported non-standard-library packages) and occupies about 11 MiB. The stripped static Linux/ARM64 binary validated with Go 1.27.1 is 6,422,688 bytes. Build output belongs in ignored `build/`, not in source control.
